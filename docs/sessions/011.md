## 1. Theory — Agent Lifecycle và AgentOps (20 phút)

### 1.1 Agent Lifecycle: từ Develop đến Release

```text
Develop
    ↓ (code commit, test)
Test
    ↓ (run eval on candidate)
Evaluate
    ↓ (compare vs baseline, quality gate)
Package
    ↓ (docker, dependencies, config)
Deploy
    ↓ (cloud run, GKE, serverless)
Observe
    ↓ (collect traces, metrics, user feedback)
    ├─ Feedback good? → Release
    └─ Issue? → Improve
Evaluate (production data)
    ↓
Improve
    ↓ (fix prompt, tool, retrieval, model)
Release
    ↓ (tag, announce, monitor)
```

**Điểm khác biệt so với MLOps**:

- **ML model**: data → train → model.pkl → test → deploy → monitor.
- **Agent**: code + prompt + tools + config → test → eval → package → deploy → observe.

Ở MLOps, model là artifact chính. Ở AgentOps, **mọi thứ** là artifact: code, prompt, model choice, tool definition, retrieval chunk strategy, evaluation dataset, guardrail policy.

### 1.2 Vì sao cần chuẩn hóa ngay ở Buổi 11

Nếu agent chưa chuẩn hóa:

- **Không reproducible**: "Tại sao output khác với hôm qua?" → không có baseline để so sánh.
- **Không track được thay đổi**: "Cái gì làm quality tốt lên?" → không biết commit/prompt/tool nào gây nên.
- **Khó package**: dependency bị conflict, secret lộ, model file chưa biết version → deploy thất bại.
- **Không scale được**: muốn chạy N worker hoặc experiment parallel → không có environment config → mỗi máy config khác.
- **Khó incident response**: "Production fail lúc 2 sáng, phải rollback" → không tag, không baseline → mất hết.

**Quy tắc**: Trước khi xây 9 buổi AgentOps, phải **chuẩn hóa 1 lần** ở Buổi 11. Sau đó, 9 buổi tiếp chỉ là xây orchestration, observability, evaluation, deployment xung quanh artifact đã chuẩn hóa này.

### 1.3 MLOps vs AgentOps: Bảng so sánh

| Khía cạnh             | MLOps                           | AgentOps                                      |
| --------------------- | ------------------------------- | --------------------------------------------- |
| **Artifact chính**    | Model weights (.pkl, .pt, .h5)  | Code + Prompt + Model + Tools + Config        |
| **Versioning**        | Model version (v1.0, v2.0)      | Semantic versioning cho tất cả thành phần     |
| **Test**              | Metrics (accuracy, F1, AUC)     | Trajectory, token usage, cost, latency        |
| **Evaluate**          | Golden dataset + test set       | Eval dataset + regression cases + live traces |
| **Config**            | Hyperparameter (lr, batch_size) | Prompt, model choice, tools, retrieval params |
| **Failure detection** | Model drift (data/label shift)  | Quality regression, cost spike, tool failure  |
| **Rollback**          | Swap model version              | Revert code + prompt + config tag             |
| **Observability**     | Metrics + data distribution     | Traces (trajectory) + metrics + eval results  |

## 2. Deep dive — Dependency, Config, Versioning (25 phút)

### 2.1 Dependency management: từ pip install đến lock file

**Mức 1: Không có lock** (nguy hiểm)

```bash
pip install anthropic langgraph qdrant-client
# Mỗi lần install, version có thể khác → dev máy A khác máy B
```

**Mức 2: requirements.txt với pin minor**

```
# requirements.txt
anthropic==0.39.0
langgraph==0.2.7
qdrant-client==1.9.1
python-dotenv>=0.21.0
```

Tốt hơn, nhưng mục tiêu là **reproducible build**.

**Mức 3: Lock file** (production standard)

```bash
# Cài pip-tools
pip install pip-tools

# Viết requirements.in
cat > requirements.in << 'EOF'
anthropic>=0.39.0
langgraph>=0.2.0
qdrant-client>=1.9.0
python-dotenv
FastAPI>=0.100
EOF

# Compile → lock
pip-compile requirements.in --resolver=backtracking -o requirements.lock

# Cài từ lock
pip install -r requirements.lock
```

File `requirements.lock` chứa toàn bộ dependency tree với version chính xác + hash:

```
# requirements.lock (excerpt)
anthropic==0.39.2 \
    --hash=sha256:abc123... \
    --hash=sha256:def456...
langgraph==0.2.7 \
    --hash=sha256:ghi789...
pydantic==2.7.1 \
    --hash=sha256:jkl012...
# ... tất cả transitive dependencies
```

**Lợi ích**:

- `pip install -r requirements.lock` trên máy khác 100% giống nhau.
- Biết chính xác cái gì upgrade mỗi lần.
- Có hash → detect tampering (security).

**Thực hành**:

```bash
# Setup script mẫu
# scripts/setup_env.sh
#!/bin/bash
set -e

PYTHON_VERSION=3.11
VENV_DIR=.venv

# Tạo venv
python${PYTHON_VERSION} -m venv ${VENV_DIR}
source ${VENV_DIR}/bin/activate

# Upgrade pip
pip install --upgrade pip pip-tools

# Install từ lock
pip install -r requirements.lock

echo "✓ Environment ready at ${VENV_DIR}"
echo "✓ Activate: source ${VENV_DIR}/bin/activate"
```

### 2.4 Tại sao agent cần versioning hơn API thông thường

**API thông thường**: endpoint chạy code ở server. Upgrade code → upgrade mọi request. Không cần versioning individual component.

**Agent**: Mỗi run **có thể khác** vì:

- Model có thể chọn tool khác tùy prompt.
- Retrieval kết quả phụ thuộc embeddings model + knowledge base timestamp.
- Outcome phụ thuộc eval dataset.
- Cost phụ thuộc model + retrieval params.

→ Để **so sánh công bằng**, cần snapshot toàn bộ component cùng lúc. Đó là versioning.

**Ví dụ failure**:

```
Production baseline (release-1.0.0):
- Model: Claude Opus 4
- Eval dataset: 50 cases
- Task success: 87%
- Cost: $0.24/task
- Latency: 8.5s

Vài ngày sau, prompt cần improve:
- Update prompts/system.md
- Rerun eval: 89% (tốt!)
- Deploy mà quên update retrieval knowledge

Kết quả:
- Production eval: 86% (??? Tệ hơn?)

Tìm nguyên nhân:
- Không biết retrieval knowledge có update không
- Không biết model có đổi không
- Không snapshot eval dataset

Mà đã tag release-1.0.1, vậy cách nào biết cái gì sai?
→ Phải có version component từng cái.
```

## Appendix: Shell script — setup_env.sh

```bash
#!/bin/bash
# scripts/setup_env.sh — Automated environment setup

set -e  # Exit on error

PYTHON_VERSION=${PYTHON_VERSION:-3.11}
VENV_DIR=${VENV_DIR:-.venv}
ENV=${ENV:-dev}

echo "🔧 Setting up agent environment..."
echo "  Python: $PYTHON_VERSION"
echo "  Venv: $VENV_DIR"
echo "  Environment: $ENV"

# Check Python version
if ! command -v python${PYTHON_VERSION} &> /dev/null; then
    echo "❌ Python $PYTHON_VERSION not found. Install it first."
    exit 1
fi

# Create venv
if [ -d "$VENV_DIR" ]; then
    echo "ℹ️  $VENV_DIR already exists. Skipping creation."
else
    echo "📦 Creating virtual environment..."
    python${PYTHON_VERSION} -m venv "$VENV_DIR"
fi

# Activate venv
source "$VENV_DIR/bin/activate"

# Upgrade pip
echo "📦 Upgrading pip..."
pip install --upgrade pip setuptools

# Install dependencies
echo "📦 Installing dependencies from requirements.lock..."
if [ -f "requirements.lock" ]; then
    pip install -r requirements.lock
else
    echo "❌ requirements.lock not found!"
    exit 1
fi

# Load environment
echo "⚙️  Loading environment configuration..."
if [ -f ".env.$ENV" ]; then
    export $(cat ".env.$ENV" | grep -v '^#' | xargs)
    echo "  Loaded .env.$ENV"
else
    echo "⚠️  .env.$ENV not found. Using defaults."
fi

# Verify setup
echo "✅ Verifying setup..."
python -c "import anthropic; print('  ✓ anthropic')"
python -c "import langgraph; print('  ✓ langgraph')"
python -c "import qdrant_client; print('  ✓ qdrant_client')"

echo ""
echo "✅ Environment ready!"
echo ""
echo "Next steps:"
echo "  1. Activate venv: source $VENV_DIR/bin/activate"
echo "  2. Edit .env.$ENV with your secrets"
echo "  3. Run baseline: python scripts/run_baseline.py"
echo ""
```
