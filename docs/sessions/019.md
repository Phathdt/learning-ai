## 1. Theory — Synchronous Agent vấn đề (20 phút)

### 1.1 Request-response loop: khi nào phá vỡ

Từ Buổi 9, agent API chạy theo mô hình:

```text
Client → HTTP Request (timeout 30s)
         ↓
         FastAPI
         ↓
         Agent Loop (turn 1, 2, 3, ...)
         ↓
         HTTP Response (hay timeout)
```

Ba vấn đề xảy ra khi agent chạy lâu (> 10s):

| Vấn đề                  | Triệu chứng                                              | Gốc rễ                                                  |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------------------- |
| **Connection timeout**  | Client nhận 504 sau 30s, dù agent còn chạy               | HTTP timeout chuẩn; cloud load balancer ngắt connection |
| **User disconnect**     | User đóng browser, agent vẫn tốn resources               | TCP connection đã đóng nhưng worker không biết          |
| **Worker crash**        | Agent ở giữa chừng, mất 45 phút công việc                | Process OOM, SIGTERM deploy, machine restart            |
| **No resume mechanism** | Phải chạy lại từ đầu (lưu trữ từng lần, retry từ step 1) | Session state không persist, checkpoint không có        |
| **Resource contention** | Nhiều task cùng lúc → CPU/memory spike, một task "đói"   | No concurrency limit, no backpressure                   |
| **Cost explosion**      | Long task tốn 10× model token, fail → retry tốn thêm     | Exponential cost, không có early stopping               |

Theo [Anthropic production patterns 2024](https://www.anthropic.com), dưới 5s letime OK với sync. Trên 30s → bắt buộc async queue.

### 1.2 Durable architecture: Client → Queue → Worker

Giải pháp: tách HTTP request khỏi execution.

```text
Client                      API                          Queue            Worker
 │                           │                             │                 │
 ├─ POST /tasks ────────────>│ Validate + create task      │                 │
 │                           │ (task_id, input, status)    │                 │
 │                           │<─ 200 OK + {task_id}        │                 │
 │                           │                             │                 │
 │                           └──── Enqueue ────────────────>│                 │
 │                                                          │                 │
 │                           [HTTP response sent immediately, client free]    │
 │                                                          │                 │
 │  ┌─ GET /tasks/{id}/status ──>│                        │  Dequeue       │
 │  │    (polling)                │                        │  Execute agent  │
 │  └─ 200 OK {status, progress}  │                        │  Checkpoint     │
 │                                │<──── Update DB ────────┤  (every N step) │
 │                                                          │                 │
 │                                                          │  Crash? →       │
 │                                                          │  Restart        │
 │                                                          │  Resume ────────→ Agent picks up
 │
 │  ┌─ GET /tasks/{id}/result ──>│ Query state store    └──> (task complete)
 │  │    (final)                  │<─ 200 + {result}
 │  └─ {agent_output}
```

Bốn thành phần cốt lõi:

| Thành phần      | Trách nhiệm                                    | Implementation tùy chọn          |
| --------------- | ---------------------------------------------- | -------------------------------- |
| **API**         | Tiếp nhận, validate, create task, return ID    | FastAPI handler                  |
| **Queue**       | Lưu task + metadata, deliver đến worker        | Redis Streams, RabbitMQ, PgSQL   |
| **Worker**      | Dequeue, execute agent, checkpoint, reschedule | Python threading/multiprocessing |
| **State Store** | Lưu task state, progress, result               | PostgreSQL, Redis                |

### 1.3 Task lifecycle

```text
created (API)
   ↓
queued (enqueued)
   ↓
running (worker dequeued)
   ├─ progress event 1 (agent thinking...)
   ├─ progress event 2 (tool call...)
   ├─ progress event 3 (checkpoint)
   ↓
completed (success) — save result
   OR
failed (exception) — save error
   ↓
retrying (backoff) — re-enqueue
   ├─ attempt 1: delay 1s
   ├─ attempt 2: delay 2s
   ├─ attempt 3: delay 4s
   ├─ attempt 4: delay 8s
   ↓
completed / dead-letter (max retries exceeded)
```

Mỗi trạng thái → database record + timestamp. Không có state mất.

### 1.4 Core concepts

| Khái niệm          | Định nghĩa                                                     | Ví dụ                                    |
| ------------------ | -------------------------------------------------------------- | ---------------------------------------- |
| **Message queue**  | Data structure lưu task message, FIFO hoặc priority-based      | Redis Streams: `task:pending`            |
| **Worker**         | Process/thread poll queue, dequeue, execute, checkpoint        | Python loop: `while True: dequeue()`     |
| **Task ID**        | UUID duy nhất, dùng để query status/result                     | `task_abc123`                            |
| **State store**    | Persist task state: input, status, progress, error, result     | PostgreSQL table `tasks`                 |
| **Checkpoint**     | Snapshot agent state sau N step, để resume                     | LangGraph checkpoint + task metadata     |
| **Retry**          | Nếu fail, re-enqueue với exponential backoff                   | Attempt 1 @1s, 2 @2s, 3 @4s, etc         |
| **Backoff**        | Delay tăng giữa retry để tránh thundering herd                 | `2^attempt` hoặc capped `min(300s, 2^n)` |
| **Dead-letter Q**  | Queue cho task fail lần thứ N (sau manual inspection)          | `dead_letters` topic                     |
| **Idempotency**    | Gửi duplicate message → kết quả giống, không side effect thêm  | Check `task_id` tồn tại trước execute    |
| **Cancellation**   | Client cancel task trước khi complete → worker dừng gracefully | `SIGTERM` signal, flag trong state       |
| **Resume**         | Worker crash → restart, đọc checkpoint, continue từ đó         | Load `thread_id`, invoke graph           |
| **Progress event** | Server emit event → client update UI real-time                 | SSE: `data: {"progress": "..."`          |

### 1.5 High throughput patterns

| Pattern             | Mô tả                                              | Trade-off                           |
| ------------------- | -------------------------------------------------- | ----------------------------------- |
| **Worker pool**     | N workers dequeue cùng lúc (concurrency control)   | Cần sync queue, quy định queue mode |
| **Concurrency**     | Chỉ định task chạy song song bao nhiêu cái         | Trade memory vs latency             |
| **Backpressure**    | Nếu queue > threshold, reject new task (hoặc wait) | Client phải retry exponential       |
| **Rate limiting**   | Chỉ định X task/user/sec                           | Token bucket algorithm              |
| **Queue depth**     | Monitor queue length, alert nếu > threshold        | + observability                     |
| **Per-user quotas** | User A chỉ được Y task cùng lúc                    | Namespace queue hoặc priority queue |

Ví dụ high throughput setup:

```
Redis Streams: XADD, XREAD, XACK
  ├─ Stream: task:pending (unbounded, backpressure tại API)
  ├─ Consumer Group: workers (auto ack on complete)
  └─ Per-user rate: 5 tasks/sec via token bucket

Worker Pool: 8 workers
  ├─ Worker 1–8: concurrent XREAD (block 1s)
  ├─ Execute agent (sync, 10–120s per task)
  ├─ Checkpoint saved to PostgreSQL
  └─ Mark complete: XACK (auto requeue if crashed)

Observability:
  ├─ Queue depth: XLEN task:pending
  ├─ Consumer lag: XINFO GROUPS
  └─ P95 latency: timestamp tracking
```

## 2. Deep dive — Queue + Worker + Idempotency (30 phút)

### 2.1 Message queue implementation: Redis Streams vs PostgreSQL

Hai tuỳ chọn phổ biến:

| Tính năng            | Redis Streams                      | PostgreSQL LISTEN/NOTIFY          |
| -------------------- | ---------------------------------- | --------------------------------- |
| **Storage model**    | In-memory (persistent via RDB/AOF) | ACID transaction log              |
| **Consumer group**   | Native (automatic re-delivery)     | Manual polling / trigger          |
| **Backpressure**     | `MAXLEN` cap queue size            | VACUUM, sequence generator        |
| **Latency**          | Sub-millisecond                    | 5–50ms (transaction commit)       |
| **Scalability**      | Single machine (cluster possible)  | Multi-machine (replicated table)  |
| **Operational cost** | Redis instance                     | PostgreSQL instance (shared)      |
| **When use**         | High throughput, low latency       | Transactional consistency crucial |

Code mẫu — **Redis Streams**:

```python
import redis
import json
import uuid
from datetime import datetime, timedelta

r = redis.Redis()

def enqueue_task(task_input: dict, priority: int = 1) -> str:
    task_id = str(uuid.uuid4())
    task_data = {
        "id": task_id,
        "input": json.dumps(task_input),
        "status": "queued",
        "created_at": datetime.utcnow().isoformat(),
        "priority": priority,  # for ZSET-based priority queue
    }
    # Enqueue to pending stream
    r.xadd("task:pending", {"data": json.dumps(task_data)})
    # Save to DB for durability
    save_task_to_db(task_id, task_input, "queued")
    return task_id

def worker_loop(worker_id: str, batch_size: int = 1):
    # Create consumer group if not exists
    try:
        r.xgroup_create("task:pending", "workers", id="0", mkstream=True)
    except redis.ResponseError:
        pass  # group already exists

    while True:
        # Block read: wait for new message
        messages = r.xreadgroup("workers", worker_id, {"task:pending": ">"},
                               count=batch_size, block=1000)
        if not messages:
            continue

        for stream_key, stream_msgs in messages:
            for msg_id, msg_data in stream_msgs:
                task_data = json.loads(msg_data[b"data"])
                task_id = task_data["id"]

                try:
                    print(f"[{worker_id}] execute task {task_id}")
                    result = execute_agent(task_data["input"])
                    update_task_to_db(task_id, "completed", result)
                    r.xack("task:pending", "workers", msg_id)
                except Exception as e:
                    print(f"[{worker_id}] error: {e}")
                    # Handle retry (manual or queue resubmission)
                    handle_task_error(task_id, str(e))
```

Code mẫu — **PostgreSQL LISTEN/NOTIFY**:

```python
import psycopg2
import psycopg2.extras
import json
import select

def enqueue_task_pg(conn, task_input: dict) -> str:
    task_id = str(uuid.uuid4())
    with conn.cursor() as cur:
        cur.execute("""
            INSERT INTO tasks (id, input, status, created_at)
            VALUES (%s, %s, %s, NOW())
        """, (task_id, json.dumps(task_input), "queued"))
        conn.commit()
        # Notify workers
        cur.execute("NOTIFY task_queued, %s", (task_id,))
    return task_id

def worker_loop_pg(conn_str: str):
    conn = psycopg2.connect(conn_str)
    conn.set_isolation_level(psycopg2.extensions.ISOLATION_LEVEL_AUTOCOMMIT)

    with conn.cursor() as cur:
        cur.execute("LISTEN task_queued")

    while True:
        # Wait for notification
        if select.select([conn], [], [], 5) == ([], [], []):
            # Timeout: poll DB for pending tasks
            with conn.cursor() as cur:
                cur.execute("SELECT id, input FROM tasks WHERE status='queued' LIMIT 1")
                row = cur.fetchone()
                if not row:
                    continue
                task_id, task_input = row
        else:
            # Got notification
            conn.poll()
            while conn.notifies:
                notify = conn.notifies.pop(0)
                task_id = notify.payload
                with conn.cursor() as cur:
                    cur.execute("SELECT input FROM tasks WHERE id=%s", (task_id,))
                    row = cur.fetchone()
                    if not row:
                        continue
                    task_input = row[0]

        # Execute
        try:
            print(f"[worker] execute {task_id}")
            result = execute_agent(task_input)
            with conn.cursor() as cur:
                cur.execute("""
                    UPDATE tasks SET status=%s, result=%s, completed_at=NOW()
                    WHERE id=%s
                """, ("completed", json.dumps(result), task_id))
                conn.commit()
        except Exception as e:
            # Error handling
            with conn.cursor() as cur:
                cur.execute("""
                    UPDATE tasks SET status=%s, error=%s, attempt=attempt+1
                    WHERE id=%s
                """, ("failed", str(e), task_id))
                conn.commit()
```

### 2.2 Retry + backoff strategy

Production retry logic:

```python
import time
import math

def calculate_backoff(attempt: int, base: int = 2, max_delay: int = 300) -> int:
    """Exponential backoff with cap"""
    delay = min(base ** attempt, max_delay)
    return delay + random.randint(0, int(delay * 0.1))  # jitter

def handle_task_error(task_id: str, error: str, db_conn):
    with db_conn.cursor() as cur:
        cur.execute("""
            SELECT attempt, max_retries FROM tasks WHERE id=%s
        """, (task_id,))
        attempt, max_retries = cur.fetchone()

        if attempt >= max_retries:
            # Move to dead-letter queue
            cur.execute("""
                UPDATE tasks SET status=%s, completed_at=NOW()
                WHERE id=%s
            """, ("dead-letter", task_id))
            db_conn.commit()
            # Alert ops
            alert_ops(f"Task {task_id} exceeded max retries")
        else:
            delay = calculate_backoff(attempt)
            retry_at = datetime.utcnow() + timedelta(seconds=delay)
            cur.execute("""
                UPDATE tasks
                SET status=%s, attempt=%s, retry_at=%s, error=%s
                WHERE id=%s
            """, ("retrying", attempt + 1, retry_at, error, task_id))
            # Re-enqueue at retry_at
            schedule_retry(task_id, retry_at)
            db_conn.commit()
```

### 2.3 Idempotency: duplicate delivery safety

Khi network flaky, cùng message có thể deliver 2+ lần. Phải ensure:

- Execution 1: side effect xảy ra, save result
- Execution 2, 3, ...: cùng kết quả, không side effect thêm

Pattern:

```python
def execute_task_idempotent(task_id: str, db_conn):
    # Step 1: Check idempotency token
    with db_conn.cursor() as cur:
        cur.execute("""
            SELECT status, result FROM tasks WHERE id=%s
        """, (task_id,))
        row = cur.fetchone()
        if row and row[0] in ("completed", "failed", "dead-letter"):
            # Already processed
            print(f"Task {task_id} already {row[0]}, skip")
            return row[1]  # return cached result

    # Step 2: Mark as processing (atomic)
    with db_conn.cursor() as cur:
        cur.execute("""
            UPDATE tasks SET status=%s WHERE id=%s AND status=%s
        """, ("processing", task_id, "queued"))
        if cur.rowcount == 0:
            # Someone else is processing, return
            print(f"Task {task_id} already processing by another worker")
            return None
        db_conn.commit()

    # Step 3: Execute
    try:
        result = execute_agent_with_checkpoint(task_id)
        # Step 4: Atomically save result + mark complete
        with db_conn.cursor() as cur:
            cur.execute("""
                UPDATE tasks SET status=%s, result=%s, completed_at=NOW()
                WHERE id=%s
            """, ("completed", json.dumps(result), task_id))
            db_conn.commit()
        return result
    except Exception as e:
        # Rollback: mark as queued again for retry
        with db_conn.cursor() as cur:
            cur.execute("""
                UPDATE tasks SET status=%s, error=%s
                WHERE id=%s AND status=%s
            """, ("queued", str(e), task_id, "processing"))
            db_conn.commit()
        raise
```

### 2.4 Worker crash recovery

Worker chạy agent ở giữa chừng, process OOM/SIGTERM. Recover thế nào?

**Checkpoint mechanism** (LangGraph + custom):

```python
def execute_agent_with_checkpoint(task_id: str, db_conn):
    """Execute agent, checkpoint progress, resume on crash"""

    # Load task
    with db_conn.cursor(row_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute("SELECT input, checkpoint_thread_id FROM tasks WHERE id=%s", (task_id,))
        task = cur.fetchone()

    task_input = json.loads(task["input"])
    thread_id = task["checkpoint_thread_id"] or str(uuid.uuid4())

    # Initialize agent graph with checkpointer
    conn = sqlite3.connect(":memory:")  # or PostgreSQL for production
    checkpointer = SqliteSaver(conn)
    app = build_agent_graph().compile(checkpointer=checkpointer)

    config = {"configurable": {"thread_id": thread_id}}

    # Resume or start
    print(f"[{task_id}] Starting agent with thread_id={thread_id}")

    try:
        # Stream execution, checkpoint auto-saved after each node
        for chunk in app.stream({"task": task_input["query"]}, config):
            # Update progress in DB
            for node, state in chunk.items():
                progress = {
                    "node": node,
                    "iteration": state.get("iteration"),
                    "status": state.get("status"),
                }
                with db_conn.cursor() as cur:
                    cur.execute("""
                        UPDATE tasks SET progress=%s, updated_at=NOW()
                        WHERE id=%s
                    """, (json.dumps(progress), task_id))
                    db_conn.commit()

        final_state = app.get_state(config).values
        return final_state

    except Exception as e:
        # Save checkpoint ID for resume
        state = app.get_state(config)
        with db_conn.cursor() as cur:
            cur.execute("""
                UPDATE tasks SET checkpoint_thread_id=%s, error=%s
                WHERE id=%s
            """, (thread_id, str(e), task_id))
            db_conn.commit()
        raise
```

### 2.5 High throughput: concurrency + backpressure

```python
def api_with_backpressure(queue_depth_limit: int = 1000):
    @app.post("/tasks")
    def create_task(request: TaskRequest):
        # Check queue depth
        depth = r.xlen("task:pending")
        if depth > queue_depth_limit:
            return {"error": "queue full"}, 503  # Service Unavailable

        # Rate limit per user
        user_id = request.user_id
        token_key = f"rate:{user_id}"
        tokens = r.get(token_key)

        if tokens and int(tokens) <= 0:
            return {"error": "rate limit exceeded"}, 429

        # Deduct token (token bucket algorithm)
        r.decr(token_key)
        r.expire(token_key, 60)  # refill after 60s

        # Enqueue
        task_id = enqueue_task(request)
        return {"task_id": task_id}

# Worker pool: 8 workers, concurrent
import multiprocessing
import threading

def start_worker_pool(num_workers: int = 8):
    workers = []
    for i in range(num_workers):
        t = threading.Thread(target=worker_loop, args=(f"worker-{i}",))
        t.daemon = True
        t.start()
        workers.append(t)
    print(f"Started {num_workers} workers")
```

### 4.2 Bài tập chính

**Nâng cấp Operations Intelligence Agent từ Buổi 12–18.**

**Yêu cầu:**

1. **API Layer** — `POST /tasks` endpoint:
   - Nhận `{"query": "...", "user_id": "..."}`.
   - Validate, create task record, enqueue.
   - Trả `{"task_id": "...", "status": "queued"}`.
   - Implement backpressure: nếu queue > 100, reject.
   - Rate limit: 5 tasks/user/sec (token bucket).

2. **Message Queue** — Redis Streams:
   - Enqueue task to `task:pending`.
   - Consumer group `workers`.
   - Auto re-delivery nếu worker crash (before ACK).

3. **Worker Pool** — 3 workers concurrent:
   - Dequeue từ `task:pending`.
   - Execute agent loop (LangGraph từ Buổi 2).
   - Checkpoint sau mỗi node.
   - ACK on success, manual requeue on error (exponential backoff).

4. **State Persistence** — PostgreSQL:
   - Task table (schema trên).
   - Update status: queued → processing → completed.
   - Save result, error, progress.

5. **Progress Tracking** — SSE endpoint `GET /tasks/{id}/progress`:
   - Emit event mỗi agent node: `{"node": "agent", "iteration": 2, ...}`.
   - Client subscribe via EventSource.

6. **Status Query** — `GET /tasks/{id}`:
   - Trả `{"task_id": "...", "status": "...", "progress": {...}, "result": {...}}`.

7. **Cancellation** — `DELETE /tasks/{id}`:
   - Nếu queued → remove từ queue.
   - Nếu processing → flag, worker sẽ graceful stop.

8. **Worker Management**:

def create_task(user_id: str, query: str, db_conn) -> str:

    conn = get_db()
    with conn.cursor() as cur:
        cur.execute("""

            VALUES (%s, %s, %s, NOW())

    with db_conn.cursor() as cur:

            UPDATE tasks
            SET status=%s, result=%s, error=%s, updated_at=NOW()
            WHERE id=%s
        """, (status, json.dumps(result) if result else None, error, task_id))
        db_conn.commit()

# ============ Worker ============
def worker_process(worker_id: str):
    """Run in background"""
    print(f"[{worker_id}] starting")
    conn = get_db()

    try:
        r.xgroup_create("task:pending", "workers", id="0", mkstream=True)
    except redis.ResponseError:
        pass  # group exists

    while True:
        try:
            messages = r.xreadgroup(
                "workers", worker_id,
                {"task:pending": ">"}, count=1, block=1000
            )
            if not messages:
                continue

            for stream, msg_list in messages:
                for msg_id, msg_data in msg_list:
                    task_id = msg_data["task_id"]
                    query = msg_data["query"]

                    print(f"[{worker_id}] execute {task_id}")

                    try:
                        # Load task, checkpoint
                        update_task_status(task_id, "processing", conn)

                        # Execute agent
                        result = execute_agent_task(task_id, query, conn)

                        # Success
                        update_task_status(task_id, "completed", conn, result=result)
                        r.xack("task:pending", "workers", msg_id)

                    except Exception as e:
                        print(f"[{worker_id}] error: {e}")
                        # Retry logic
                        handle_task_error(task_id, str(e), conn)
                        r.xack("task:pending", "workers", msg_id)

        except Exception as e:
            print(f"[{worker_id}] loop error: {e}")
            time.sleep(1)

# ============ FastAPI ============
@asynccontextmanager
async def lifespan(app: FastAPI):
    # Startup: start worker processes
    import threading
    for i in range(3):
        t = threading.Thread(target=worker_process, args=(f"worker-{i}",), daemon=True)
        t.start()
    print("Workers started")
    yield
    # Shutdown

@app.post("/tasks")
def post_tasks(query: str, user_id: str = "default"):
    # Check queue depth + rate limit
    depth = r.xlen("task:pending")
    if depth > 100:
        raise HTTPException(status_code=503, detail="Queue full")

    # Token bucket rate limit
    token_key = f"rate:{user_id}"
    tokens = r.decr(token_key)
    if tokens <= 0:
        raise HTTPException(status_code=429, detail="Rate limit")
    r.expire(token_key, 60)

    db_conn = get_db()
    task_id = create_task(user_id, query, db_conn)
    db_conn.close()

    return {"task_id": task_id, "status": "queued"}

@app.get("/tasks/{task_id}")
def get_task_status(task_id: str):
    db_conn = get_db()
    with db_conn.cursor(row_factory=psycopg2.extras.RealDictCursor) as cur:
        cur.execute("""
            SELECT id, status, progress, result, error, updated_at FROM tasks WHERE id=%s
        """, (task_id,))
        row = cur.fetchone()
    db_conn.close()

    if not row:
        raise HTTPException(status_code=404)

    return {
        "task_id": row["id"],
        "status": row["status"],
        "progress": json.loads(row["progress"]) if row["progress"] else None,
        "result": json.loads(row["result"]) if row["result"] else None,
        "error": row["error"],
        "updated_at": row["updated_at"].isoformat(),
    }

@app.get("/tasks/{task_id}/progress")
async def stream_task_progress(task_id: str) -> StreamingResponse:
    async def event_generator() -> AsyncGenerator[str, None]:
        db_conn = get_db()
        last_progress = None

        while True:
            with db_conn.cursor(row_factory=psycopg2.extras.RealDictCursor) as cur:
                cur.execute("""
                    SELECT status, progress FROM tasks WHERE id=%s
                """, (task_id,))
                row = cur.fetchone()

            if not row:
                yield f"data: {json.dumps({'error': 'not found'})}\n\n"
                break

            progress = json.loads(row["progress"]) if row["progress"] else {}
            if progress != last_progress:
                yield f"data: {json.dumps(progress)}\n\n"
                last_progress = progress

            if row["status"] in ("completed", "failed"):
                break

            await asyncio.sleep(0.5)

        db_conn.close()

    return StreamingResponse(event_generator(), media_type="text/event-stream")

@app.delete("/tasks/{task_id}")
def cancel_task(task_id: str):
    db_conn = get_db()
    with db_conn.cursor() as cur:
        cur.execute("UPDATE tasks SET status='cancelled' WHERE id=%s AND status='queued'", (task_id,))
        db_conn.commit()
    db_conn.close()
    return {"status": "cancelled"}
