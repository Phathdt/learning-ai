## 1. Theory — Image vs Container (20 phút)

### 1.1 Tại sao Docker

Buổi 11-12, agent chạy tốt trên máy developer với Python 3.11, dependencies pinned. Nhưng khi chuyển sang máy khác hoặc production:

- "Trên máy tôi chạy được" (It works on my machine).
- Python version khác → package compile sai.
- System library thiếu → import fail.
- Port đã bị chiếm → connection refused.
- Database schema khác → query fail.

**Docker** giải quyết: Một **image** là snapshot toàn bộ filesystem + runtime + environment, reproducible trên bất kỳ máy nào.

Container = image chạy.

Analogy: Image là **blueprint**, container là **tòa nhà chạy từ blueprint đó**.

### 1.2 Image và Layer

Dockerfile là một tập các instruction. Mỗi instruction tạo ra một **layer**.

```dockerfile
FROM python:3.11-slim
# Layer 0: base OS + Python runtime (cached từ Docker Hub)

RUN apt-get update && apt-get install -y build-essential
# Layer 1: system packages

COPY requirements.txt .
RUN pip install -r requirements.txt
# Layer 2: Python dependencies

COPY src/ /app/src/
# Layer 3: application code

EXPOSE 8000
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0"]
# No new layer
```

**Quan trọng**: Mỗi layer là immutable. Khi bạn rebuild image sau khi change code (layer 3), Docker sử dụng lại layer 0, 1, 2 từ cache. Chỉ rebuild layer 3.

Điều này là lý do **thứ tự instruction** rất quan trọng. Nếu bạn COPY code trước pip install:

```dockerfile
# ❌ Xấu: mỗi khi change code → rebuild tất cả layer deps
COPY src/ /app/src/
RUN pip install -r requirements.txt
```

Thì mỗi lần bạn chỉnh code, docker phải rebuild toàn bộ pip install.

```dockerfile
# ✅ Tốt: chỉ rebuild layer code, reuse layer deps
RUN pip install -r requirements.txt
COPY src/ /app/src/
```

### 1.3 Build cache strategy

**Chain of layers**:

```
FROM (cached)
  ↓
RUN apt-get (cached nếu không thay đổi)
  ↓
COPY requirements.txt (cached nếu file không thay đổi)
  ↓
RUN pip install (cached nếu requirements.txt không thay đổi) ← KEY
  ↓
COPY src/ (rebuilt nếu code thay đổi)
  ↓
...final layer
```

**Build time**:

- Lần đầu: 3-5 phút (download + compile).
- Lần thứ 2 (chỉ change code): 5 giây (reuse 4 layers, rebuild layer code).

Chiến lược này gọi là **dockerfile.txt layering** hoặc **cache busting**.

### 1.4 Multi-stage build

Một Dockerfile có thể có nhiều `FROM` statement. Mỗi cái là một stage.

Ví dụ:

```dockerfile
# Stage 1: Builder
FROM python:3.11 as builder
WORKDIR /build
COPY requirements.txt .
RUN pip install --target ./dependencies -r requirements.txt

# Stage 2: Runtime
FROM python:3.11-slim
WORKDIR /app
COPY --from=builder /build/dependencies ./dependencies
COPY src/ ./src/
ENV PYTHONPATH=/app/dependencies
CMD ["uvicorn", "src.main:app"]
```

**Lợi ích**:

- **Slim base image**: runtime stage dùng `python:3.11-slim` (~100MB) thay vì `python:3.11` (~300MB). Chỉ copy dependencies cần thiết.
- **No build tools**: builder stage có gcc, build-essential. Runtime stage không → image nhỏ và an toàn hơn (ít tool để attacker dùng).
- **Faster deployment**: nhỏ hơn → push/pull nhanh hơn.

### 1.5 Năm nguyên tắc Dockerfile

| #   | Nguyên tắc                    | Ý nghĩa                                                          | Ví dụ                                                      |
| --- | ----------------------------- | ---------------------------------------------------------------- | ---------------------------------------------------------- |
| 1   | Minimal base image            | Chọn base image nhỏ nhất đủ dùng                                 | `python:3.11-slim` (~150MB) vs `python:3.11` (~300MB)      |
| 2   | Non-root user                 | Chạy app dưới user khác root → giới hạn damage nếu bị compromise | `RUN useradd -m appuser` + `USER appuser`                  |
| 3   | Deterministic dependencies    | Pin version cụ thể, không dùng `latest`                          | `requirements.txt` với `package==1.2.3` hoặc `poetry.lock` |
| 4   | Cache dependencies separately | COPY requirements → pip install trước COPY code                  | Nếu code change, reuse pip layer                           |
| 5   | No secrets in image           | Không hard-code API keys, database URL                           | Dùng environment variables hoặc build args                 |

## 2. Deep Dive — Dependency Pinning, Secrets, Networking (30 phút)

### 2.1 Dependency pinning

**Vấn đề**: Nếu Dockerfile chỉ nói "pip install fastapi", Docker pull latest version. Nếu version mới có breaking change → app break.

**Giải pháp**: Pin version cụ thể trong `requirements.txt` hoặc `pyproject.toml`:

```
# requirements.txt
fastapi==0.104.1
uvicorn==0.24.0
anthropic==0.15.2
qdrant-client==2.5.0
sqlalchemy==2.0.23
```

Hoặc dùng `requirements.lock` từ `pip-tools` hoặc `poetry.lock` từ Poetry (còn tốt hơn, include transitive deps).

**Best practice**: Commit lock file vào git. Build image từ lock file, không từ `requirements.txt` thôi.

```dockerfile
COPY pyproject.toml poetry.lock ./
RUN pip install poetry && poetry install --no-root
```

### 2.2 Environment variables và Secrets

**Không làm thế này**:

```dockerfile
# ❌ NGUY HIỂM: secret lộ ra image layer history
ENV DATABASE_URL="postgresql://user:PASSWORD@localhost/db"
ENV ANTHROPIC_API_KEY="sk-xxx"
```

Khi một layer bị expose (ví dụ push image nhầm lên public registry), secret vĩnh viễn ở trong layer history. Docker history layer không thể xóa.

**Cách đúng**:

```dockerfile
# ✅ Build-time secret (chỉ dùng lúc build)
RUN --mount=type=secret,id=api_key \
    cat /run/secrets/api_key > /tmp/setup.sh && \
    bash /tmp/setup.sh && \
    rm /tmp/setup.sh

# ✅ Runtime environment (inject lúc run)
ENV LOG_LEVEL=INFO
```

Gọi docker build:

```bash
docker build --secret api_key=/path/to/key.txt -t agent:latest .
```

Hoặc trong docker-compose, dùng `env_file` hoặc `environment` (load từ shell env hoặc .env file, không hard-code).

### 2.4 Networking

Khi chạy multi-container (FastAPI + Qdrant + PostgreSQL), container cần communicate với nhau.

**Docker network**:

```bash
# Bridge network (default): container có hostname = service name
docker network create agent-network
docker run --network agent-network --name api my-api
docker run --network agent-network --name db postgres
```

Trong FastAPI code:

```python
# fastapi/src/main.py
import os

DB_URL = os.getenv("DATABASE_URL", "postgresql://user:pass@db:5432/agentdb")
QDRANT_URL = os.getenv("QDRANT_URL", "http://qdrant:6333")
```

Container tên "db" có hostname "db" trên network → `db:5432` có thể resolve.

**Docker Compose** tự động tạo network và manage service discovery. Không cần `docker network create`.

### 2.5 Volumes

Persist data sau khi container stop/remove.

**Named volume** (Docker manage):

```dockerfile
# docker-compose.yml
services:
  postgres:
    image: postgres:15
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

Data lưu ở `/var/lib/docker/volumes/postgres_data/_data` trên host.

**Bind mount** (mount thư mục host):

```yaml
volumes:
  - ./data:/app/data
```

Dùng khi developer muốn access data trực tiếp từ host.

### 2.6 Graceful shutdown

Khi Docker stop container, Docker gửi SIGTERM signal. App có 10 giây để cleanup trước khi Docker force kill (SIGKILL).

Ở Buổi 12, FastAPI app chỉ `uvicorn src.main:app`. Uvicorn bắt SIGTERM, nhưng hãy bắt chuẩn:

```python
# src/main.py
import signal
import asyncio
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app):
    # Startup
    print("Agent starting...")
    yield
    # Shutdown
    print("Agent shutting down...")
    await app.state.agent_context.cleanup()

app = FastAPI(lifespan=lifespan)

@app.get("/health")
async def health():
    return {"status": "ok", "version": "1.0"}
```

Uvicorn tự handle SIGTERM bằng cách call lifespan shutdown hook. Không cần manual signal handler.

### 2.7 Health check

Docker có thể periodically check nếu container còn sống. Nếu health check fail, Docker có thể auto-restart.

Ở `docker-compose.yml`:

```yaml
services:
  api:
    build: .
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 40s
```

- `interval`: check mỗi 10 giây.
- `timeout`: nếu response > 5 giây → fail.
- `retries`: 3 lần fail → unhealthy.
- `start_period`: chờ 40 giây trước khi check lần đầu (để app startup).

## 3. Demo — Build Multi-Stage Image và Test (15 phút)

### 3.1 Dockerfile cho FastAPI Agent

```dockerfile
# Dockerfile
# Stage 1: Builder
FROM python:3.11 as builder

WORKDIR /build

# Install build dependencies
RUN apt-get update && apt-get install -y --no-install-recommends \
    build-essential \
    curl \
    && rm -rf /var/lib/apt/lists/*

# Copy và cache dependencies
COPY requirements.txt .
RUN pip install --upgrade pip && \
    pip install --target ./dependencies -r requirements.txt

# Stage 2: Runtime
FROM python:3.11-slim

WORKDIR /app

# Copy system-level runtime deps from builder (optional, for binary wheels)
# For pure Python packages, not strictly needed

# Copy Python dependencies from builder
COPY --from=builder /build/dependencies ./dependencies

# Create non-root user
RUN useradd -m -u 1000 appuser

# Copy application code
COPY src/ ./src/
COPY pyproject.toml ./

# Set environment
ENV PYTHONPATH=/app/dependencies:/app
ENV PYTHONUNBUFFERED=1
ENV LOG_LEVEL=INFO

# Switch to non-root user
USER appuser

# Expose port
EXPOSE 8000

# Health check
HEALTHCHECK --interval=10s --timeout=5s --retries=3 --start-period=40s \
    CMD curl -f http://localhost:8000/health || exit 1

# Start app
CMD ["python", "-m", "uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

## 5. Principles — Docker best practices (tóm tắt)

| Nguyên tắc        | Tại sao                          | Áp dụng                                  |
| ----------------- | -------------------------------- | ---------------------------------------- |
| Minimal base      | Giảm image size + attack surface | Dùng `*-slim` hoặc `*-alpine`            |
| Pin dependencies  | Reproducibility                  | `requirements.txt` + lock file           |
| Layer caching     | Tăng build speed                 | COPY deps → pip install trước COPY code  |
| Non-root user     | Security                         | `RUN useradd` + `USER appuser`           |
| No secrets        | Prevent exposure                 | Environment variables hoặc build secrets |
| Health check      | Auto recovery                    | `HEALTHCHECK` + endpoint                 |
| Graceful shutdown | Data consistency                 | Implement lifespan hook                  |
| Multi-stage       | Smaller production image         | Builder stage + runtime stage            |
| .dockerignore     | Reduce context                   | Exclude test, docs, venv                 |

## 6. Troubleshooting — Failure modes

### 6.1 OOM (Out of Memory)

```
ERROR: Docker daemon ran out of memory
```

**Giải pháp**: Tăng memory limit cho Docker Desktop:

- **macOS**: Docker Desktop → Preferences → Resources → Memory.
- **Linux**: Không có limit by default, nhưng cgroup có thể constrain. Check `/sys/fs/cgroup`.

Hoặc limit memory per-container:

```yaml
services:
  api:
    mem_limit: 512m
    memswap_limit: 1g
```

### 6.2 Port conflict

```
ERROR: bind: address already in use
```

**Giải pháp**:

```bash
# Check port 8000
lsof -i :8000

# Kill process
kill -9 <PID>

# Hoặc dùng port khác
docker run -p 8001:8000 agent-api:1.0
```

### 6.3 Health check timeout

```
Container unhealthy (health: exiting)
```

**Giải pháp**:

- Tăng `start_period` nếu app startup chậm.
- Check logs: `docker logs <container>`.
- Thử manual: `docker exec <container> curl http://localhost:8000/health`.

### 6.4 Network không kết nối

```
Could not resolve hostname 'postgres'
```

**Giải pháp**:

- Confirm services cùng network: `docker network inspect agent-network`.
- Restart containers: `docker-compose restart`.
- Check env var: `echo $DATABASE_URL`.

```
Ready for deployment to Cloud Run (Buổi 14)
```

## Supplementary — Database initialization script

Tạo `agent/scripts/init_db.sql`:

```sql
-- Initialize database schema
CREATE SCHEMA IF NOT EXISTS agent;

CREATE TABLE agent.tasks (
    id SERIAL PRIMARY KEY,
    user_id VARCHAR(255) NOT NULL,
    description TEXT NOT NULL,
    status VARCHAR(50) DEFAULT 'created',
    result JSONB,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE TABLE agent.execution_traces (
    id SERIAL PRIMARY KEY,
    task_id INTEGER REFERENCES agent.tasks(id),
    model TEXT NOT NULL,
    input_tokens INTEGER,
    output_tokens INTEGER,
    latency_ms INTEGER,
    created_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_tasks_user_id ON agent.tasks(user_id);
CREATE INDEX idx_tasks_status ON agent.tasks(status);
CREATE INDEX idx_traces_task_id ON agent.execution_traces(task_id);
```

Docker tự chạy script này khi container startup lần đầu.
