### Mục tiêu học tập (đo được)

Sau buổi học, học viên có thể:

1. **Detect** incident từ dashboard/alert: Identify anomaly (latency spike, error rate, cost jump) trong vòng 2 phút.
2. **Trace** request đầu cuối: Từ user request → API → agent span → tool call → LLM → response. Tìm điểm fail.
3. **Triage** severity: P1 (production down, data loss), P2 (degraded, manual workaround), P3 (minor, cosmetic).
4. **Contain** blast radius: Kill toxic worker, rate-limit abuse, toggle feature flag, force rollback revision.
5. **Investigate** root cause: Read logs, query state, compare baseline/candidate, test hypothesis.
6. **Mitigate** immediately: Hotfix, rollback, config change. Deploy in <15 min.
7. **Recover** durably: Verify traffic recovery, check error rates, confirm no cascading failures.
8. **Postmortem**: Write timeline, impact, 5-why root cause, contributing factors, detection miss, mitigation gap.
9. **Regression test**: Add eval case for scenario to prevent recurrence.
10. **Update runbook** cho incident pattern này.

## 1. Theory — Production Readiness Checklist (20 phút)

### 1.1 13-point Production Readiness Audit

Trước khi một agent có thể claim "production-ready", phải vượt qua 13 checkpoint:

| #   | Checkpoint                | Requirement                                                                              | Verify By                                       |
| --- | ------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------------------- |
| 1   | **API Contract**          | Request/response schema, error codes, rate limit, timeout, versioning                    | Swagger/OpenAPI + integration test              |
| 2   | **Authentication**        | User identity verified; session isolated; token refresh/expiry                           | AuthN test; session cross-check                 |
| 3   | **Authorization**         | Tool/resource access by user role; audit log; cross-tenant boundary                      | RBAC test; cross-tenant denial test             |
| 4   | **Secrets Management**    | No secrets in code/logs/config; use Secret Manager; rotation policy                      | Secret scan in CI; audit Secret Manager         |
| 5   | **Observability**         | Structured logs, metrics (rate/error/latency), traces, agent instrumentation, dashboards | Query Langfuse/Grafana; trigger alert           |
| 6   | **Evaluation & Baseline** | Eval dataset, regression suite, baseline metrics, quality gate in CD                     | Run eval; compare baseline/candidate            |
| 7   | **Security Controls**     | Input validation, prompt injection defense, tool sandbox, rate limit, IP allowlist       | Security test suite; pen test                   |
| 8   | **Backup & State**        | Checkpoint saved; task state recoverable; database backup; RTO/RPO defined               | Simulate worker crash; verify resume            |
| 9   | **Scaling & Capacity**    | Autoscaling configured; queue depth monitored; per-user quota; load test result          | Load test; queue under peak load                |
| 10  | **Cost Controls**         | Budget alert; model quota; tool call throttle; cost per request tracked                  | Review cost dashboard; trigger budget alert     |
| 11  | **Alerting & On-Call**    | PagerDuty/Slack alerts; runbook link; on-call schedule; alert fatigue <5% false positive | Trigger test alert; verify on-call response     |
| 12  | **Rollback & Canary**     | Blue-green deployment; canary traffic%; instant rollback; versioning strategy            | Deploy canary; trigger rollback; verify traffic |
| 13  | **Runbook & Postmortem**  | Incident response procedure; postmortem template; blameless culture; action tracking     | Simulate incident; execute runbook              |

**Ý nghĩa**: Mỗi checkpoint là risk mitigation. Bỏ qua 1 checkpoint = 1 failure mode mà bạn không chuẩn bị.

### 1.2 Incident Response Flow (7 bước)

Khi alert phát động:

```
Detect (< 2 min)
  ↓
Triage (< 5 min)
  ├─→ P1: Contain immediately
  ├─→ P2: Investigate in parallel
  └─→ P3: Schedule investigation
  ↓
Contain (< 15 min)
  ├─→ Kill toxic worker / rate-limit abuse
  ├─→ Toggle feature flag
  ├─→ Force rollback revision
  └─→ Redirect traffic
  ↓
Investigate (< 1 hour)
  ├─→ Read logs + traces
  ├─→ Query state/DB
  ├─→ Compare baseline vs candidate
  └─→ Test hypothesis
  ↓
Mitigate (< 15 min for hotfix)
  ├─→ Deploy fix / config change
  ├─→ Verify no regression
  └─→ Monitor 10 min
  ↓
Recover
  ├─→ Watch error rate → 0
  ├─→ Verify no cascading failures
  ├─→ Customer communication (if needed)
  └─→ Stand down
  ↓
Postmortem (within 24 hours)
  ├─→ Timeline + impact
  ├─→ Root cause (5-why)
  ├─→ Detection miss + mitigation gap
  ├─→ Corrective action (prevent recurrence)
  └─→ Regression test added
```

**Key metric**: MTTD (Mean Time to Detect) + MTTR (Mean Time to Resolve). Target: MTTD < 2 min, MTTR < 30 min.

### 1.3 Postmortem Structure (blameless)

Template bắt buộc cho mỗi incident P1/P2:

````markdown
# Incident Report: [Title]

## Impact

- Duration: 14:23–14:38 UTC (15 min)
- Users affected: ~12K requests, <1% error spike
- Revenue impact: $240 estimated (if applicable)
- SLA breach: No (target 99.9%, observed 99.87%)

## Timeline

- 14:23 UTC: Alert fires "Agent latency P95 > 5s"
- 14:24 UTC: On-call acknowledged, spun up Grafana
- 14:26 UTC: Traced to tool timeout in Qdrant retrieval
- 14:27 UTC: Checked Qdrant logs → connection pool exhausted
- 14:29 UTC: Toggled feature flag `use_retrieval=false` → immediate recovery
- 14:38 UTC: Deployed pool size increase + restarted Qdrant
- 14:42 UTC: Verified recovery, re-enabled feature flag
- 15:00 UTC: Customer impact resolved

## Root Cause

Connection pool size (10) insufficient under peak traffic surge.
Qdrant queries queued up, blocking agent loop. LLM timeout → request timeout.

## Contributing Factors

1. Load test used only 100 concurrent requests; prod saw 400
2. Qdrant connection pool hardcoded, not configurable
3. No alert on connection pool exhaustion (only alert on latency)

## Detection

Alert "Agent latency P95 > 5s" fired correctly. MTTD = 1 min ✓
But root cause took 3 min to pinpoint. Missing: connection pool saturation alert.

## Mitigation

Toggle retrieval off → immediate (15s). Better than rollback (3 min).

## Corrective Actions

1. **Immediate**: Increase Qdrant pool size from 10 → 50, deployed within 20 min
2. **This week**: Add alert on Qdrant connection pool usage > 80%
3. **This week**: Load test with 500 concurrent requests (2x expected peak)
4. **Next sprint**: Make connection pool configurable per environment

## Regression Test

```python
async def test_qdrant_pool_exhaustion():
    """Verify agent gracefully degrades if retrieval times out."""
    with mock_qdrant_pool_full():
        response = await agent.run("query")
        assert response.status == "partial"  # Falls back to no-retrieval mode
        assert response.warning == "Retrieval unavailable"
```
````

- Drafted: 2025-01-15 15:30 UTC
- Reviewed: 2025-01-15 16:00 UTC (Bob, engineering lead)
- Closed: 2025-01-15 16:30 UTC (all actions planned)

```

### 1.4 Failure Scenarios Catalog (10 common)

| # | Scenario                     | Detection Signal                          | Immediate Contain                        | Root Cause Likely                          |
|---|------------------------------|-------------------------------------------|------------------------------------------|--------------------------------------------|
| 1 | LLM provider timeout         | Agent latency spike, "API unavailable"    | Retry with backoff, fallback model       | Provider outage, quota hit, network issue  |
| 2 | Tool unavailable             | Tool error rate 100%, logs "connection"   | Disable tool, toggle feature flag        | Downstream DB/API down, wrong credentials  |
| 3 | Retrieval outage             | Retrieval latency > 30s, Qdrant 500 error | Disable retrieval, fallback to prompt    | Qdrant pool exhausted, network issue       |
| 4 | Invalid model output         | Parsing error, JSON decode fail            | Retry with different temp, rollback      | Model degradation, prompt regression       |
| 5 | Queue backlog                | Queue depth > 10K, worker lag growing     | Scale workers +50%, prioritize urgent    | Slow tool, LLM bottleneck, worker crash    |
| 6 | Worker crash                 | Worker missing from pool, task orphaned   | Restart worker, resume checkpoint        | OOM, uncaught exception, signal caught     |
| 7 | Cost spike                   | Cost/request > 3× baseline                | Rate-limit aggressive, route to cheaper  | New eval consuming tokens, bug in context  |
| 8 | Latency spike                | P95 latency > 3× baseline                 | Trace request, check tool latency        | New tool slow, LLM model degraded          |
| 9 | Security violation           | Audit log detects unauthorized access     | Kill session, revoke token, alert admin  | Compromised credential, injection attack  |
| 10| Bad release                  | Error rate spike post-deploy               | Rollback revision, re-enable old version | Prompt change, tool schema mismatch        |

## 2. Theory — Detection & Mitigation Patterns (25 phút)

### 2.1 Alert hierarchy (signal vs noise)

**Ideal**: Alert fires exactly when action needed.

| Alert Level | Latency | False Positive Rate | Example                         |
|-------------|---------|---------------------|------------------------------|
| Critical   | ASAP    | <1%                 | Error rate > 5% for 1 min    |
| High       | <2 min  | <5%                 | P95 latency > 5s for 2 min   |
| Medium     | <10 min | <10%                | Queue depth > 1K for 5 min   |
| Low        | <1 hr   | <20%                | Cost/request > 2× for 30 min |

**Anti-pattern**: Alert every anomaly. Alert fatigue → people ignore alerts.

### 2.2 Mitigation playbook examples

**Scenario 1: Agent latency spike post-release**

```

Detection: P95 latency 200ms → 5s (25× increase)
MTTD: 1 min
┌─ Immediate (0–5 min)
│ 1. Check Grafana: spike coincides with 14:22 UTC release
│ 2. Check error rate: no change → not crash, just slow
│ 3. Hypothesis: new retrieval query too complex
│ 4. Action: Rollback to previous revision
│ $ gcloud run services update-traffic agent --to-revisions agent-v42=0,agent-v41=100
│ 5. Monitor: latency → 200ms ✓
│
├─ Investigation (5–30 min)
│ 1. Compare v41 vs v42 diff: prompt changed, now includes 10KB context
│ 2. Root cause: new context compression broke Qdrant query
│ 3. Load test v42 with 200 concurrent requests: reproducible
│
└─ Fix & Re-deploy (30–60 min)

1. Revert context to v41 version
2. Add regression test: latency(context_size=100KB) < 500ms
3. Re-deploy v42+ with fix
4. Canary 10% traffic, monitor 10 min
5. Full rollout when P95 latency stable < 300ms

```

**Scenario 2: Worker crash loop**

```

Detection: Worker restart count increasing, queue lag growing
MTTD: 3 min (when queue depth alert fires)
┌─ Immediate (0–5 min)
│ 1. Check worker logs: OOM kill, then restart
│ 2. Hypothesis: task causing memory leak
│ 3. Action: Scale up workers (more replicas = distribute load)
│ $ kubectl scale deployment agent-worker --replicas=10
│ 4. Kill old pods to force restart
│ 5. Monitor: queue depth → 0, lag → 0 ✓
│
├─ Investigation (5–30 min)
│ 1. Dump heap from crashed pod
│ 2. Profile memory: LangGraph checkpoint accumulation
│ 3. Root cause: 100K iteration loop, each iteration adds to checkpoint
│ 4. Query database: this task ran 500 iterations before OOM
│
└─ Fix (30–60 min)

1. Add max_iterations = 50 guardrail
2. Add memory threshold: abort if memory > 500MB
3. Test locally: run same task, verify completes < 200MB
4. Deploy fix


## 4. Lab — Production Game Day (50 phút)

### 4.1 Setup

Mỗi team (2–3 người) nhận một production incident scenario khác nhau:

**Scenario A: Cost Spike**

```
Timestamp: 2025-01-15 13:45 UTC
Alert: Cost per request increased from $0.02 to $0.08 (4× baseline)
Background: Release deployed 30 min ago added new retrieval-heavy prompt

Your task:
1. Detect: Confirm cost spike in Grafana (cost_per_request metric)
2. Trace: Query Langfuse — find example trace, show token usage
3. Identify: New prompt consumes 50KB context (was 5KB)
4. Mitigate: Revert prompt or implement context compression
5. Verify: Cost returns to $0.02 within 5 min
6. Postmortem: Timeline, root cause, regression test
```

**Scenario B: Tool Failure Loop**

```
Timestamp: 2025-01-15 14:20 UTC
Alert: Tool error rate (sql_query) jumped to 80%
Background: Database migration ran this morning

Your task:
1. Detect: Check error logs in Langfuse — "SQL: permission denied"
2. Triage: P1 — agent cannot execute queries
3. Contain: Disable SQL tool, toggle feature flag use_database=false
4. Investigate: Connect to database, check permissions
5. Find: Migration script forgot to grant SELECT to agent service account
6. Fix: Run GRANT SELECT ON * TO agent_user
7. Test: Run one query via tool to verify
8. Postmortem: Why wasn't this caught in pre-flight check?
```

**Scenario C: Worker Crash Cascade**

```
Timestamp: 2025-01-15 15:10 UTC
Alert: Queue depth growing (now 5K tasks), error rate spike
Background: New feature released that does 10-iteration retry loop

Your task:
1. Detect: kubectl get pods → worker pods in CrashLoopBackOff
2. Contain: Scale to 20 workers (kubectl scale --replicas=20)
3. Investigate: kubectl logs agent-worker-xyz → OOM killed
4. Identify: New retry loop creates 50K LangGraph checkpoints per task
5. Fix: Add max_retries=3, test locally
6. Deploy: New image with fix
7. Verify: Queue drains, workers stable
8. Postmortem: Why wasn't memory tested in staging?
```

**Scenario D: Stale Data Leakage**

```
Timestamp: 2025-01-15 16:40 UTC
Alert: Security audit detects cross-tenant data access
Background: New retrieval query added WITHOUT tenant filter

Your task:
1. Detect: Query Langfuse for tool results containing wrong tenant data
2. Triage: P1 security incident
3. Contain: Kill feature flag retrieval_enabled=false globally
4. Investigate: Compare v42 vs v41 code — missing tenant_id filter
5. Fix: Add tenant_id to retrieval query
6. Verify: Test retrieval query returns ONLY current tenant data
7. Postmortem: How did this pass code review?
8. Add regression: Security test for cross-tenant leakage
```

### 4.2 Lab Execution (50 min = 45 min per team + 5 min debrief)

### 6.3 Key Principles to Remember

1. **Agent ≠ magic LLM call**. It's model + loop + state + tools + harness.
2. **Production ≠ shipping code**. Production = code + deploy + observe + operate + recover.
3. **Reliability ≠ avoiding failures**. Reliability = detecting failures fast + recovering fast + learning from failures.
4. **Security ≠ adding guardrails**. Security = threat model → defense-in-depth → audit.
5. **Evaluation ≠ golden dataset**. Evaluation = continuous feedback → regressions caught early → quality gate before release.

### 6.4 Quick Reference: Checklist for Your Agent

Before claiming your agent is production-ready:

- [ ] Agent loop handles timeout, retry, checkpoint, resume
- [ ] API validates input, checks auth, logs structured events
- [ ] Tools have permission boundary, error handling, audit trail
- [ ] Retrieval filtered by tenant, tested for cross-leakage
- [ ] Secrets in Secret Manager, never in code/config/logs
- [ ] Eval dataset with edge cases + adversarial cases
- [ ] Baseline metrics established (latency, cost, success rate)
- [ ] Regression suite runs in CI; gates release
- [ ] Observability: Langfuse + Grafana + structured logs
- [ ] Alerting: <2 min MTTD for P1 incidents
- [ ] Runbooks written for 10+ failure scenarios
- [ ] Postmortem process defined + blameless culture
- [ ] Rollback mechanism tested (blue-green or canary)
- [ ] Durable task execution (queue + worker + checkpoint)
- [ ] Load test done; autoscaling rules tuned
- [ ] Cost dashboard tracked; budget alerts set
- [ ] Security test suite (injection, XSS, cross-tenant)
- [ ] On-call runbook link shared with team
- [ ] Incident simulation run every quarter
