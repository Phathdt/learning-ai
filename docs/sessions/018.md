## 1. Theory — Cost & Latency Model (25 phút)

### 1.1 Vì sao cần tối ưu

Từ Buổi 16–17, ta đã có **quan sát** (traces) và **đo lường** (eval dataset). Giờ là bước **lựa chọn có chủ đích**: dịch dữ liệu thành quyết định kiến trúc.

Động cơ tối ưu:

| Khi nào                    | Động cơ                                                             | Ví dụ                                                     |
| -------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------- |
| **Cost explosion**         | Bill AWS/GCP/LLM provider quá cao, hoặc margin bị ăn mòn            | Per-run cost $5 → user mong < $0.5/run                    |
| **Latency SLA miss**       | User chờ quá lâu, UX tệ, hoặc API timeout                           | P95 latency 30s → SLA yêu cầu < 5s                        |
| **Quality regression**     | Release gần đây làm giảm eval metric                                | Task success: 92% → 87%, cần hiểu tại sao và fix          |
| **Infrastructure scaling** | Resource không theo kịp nhu cầu, hoặc cost scaling không tuyến tính | Concurrency limit 10 → cần xử lý 1000 req/s               |
| **Market requirement**     | Competitor có feature nhanh/rẻ hơn, hoặc khách yêu cầu SLA cụ thể   | Shipping industry yêu cầu latency < 2s để real-time quote |

**Nguyên tắc cốt lõi**: tối ưu luôn là trade-off. Không có "miễn phí". Mục tiêu là tối ưu **có ý thức** dựa vào dữ liệu.

### 1.2 Cost Model

Tổng chi phí per-agent-run:

$$\text{Total Cost} = C_{\text{model}} + C_{\text{tool}} + C_{\text{retrieval}} + C_{\text{infrastructure}} + C_{\text{observability}}$$

Chi tiết từng thành phần:

| Thành phần         | Công thức                                                              | Ví dụ với claude-sonnet-4            | Ghi chú                                   |
| ------------------ | ---------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------- |
| **Model input**    | `input_tokens × $price_in / 1M`                                        | 8k tok × $3 / 1M = $0.024            | Cache miss, 24k → $0.072                  |
| **Model output**   | `output_tokens × $price_out / 1M`                                      | 500 tok × $15 / 1M = $0.0075         | Dùng temp=0 giảm randomness → đầu ra ngắn |
| **Tool/API**       | `num_tool_calls × cost_per_call`                                       | 3 calls × $0.01/SQL = $0.03          | Cache query result giảm được              |
| **Retrieval**      | `retrieval_queries × cost_per_query + embedding_tokens × $price_embed` | 2 queries × $0.001 + 1k tok = $0.003 | Rerank: +$0.0015 nhưng tăng precision     |
| **Infrastructure** | `cpu_seconds × $rate_cpu + memory_gb_seconds × $rate_mem + storage_gb` | 12s × $0.0002 = $0.0024              | Autoscaling giảm idle cost                |
| **Observability**  | `trace_events × $price_per_event + storage_gb × $rate_storage`         | 200 events × $0.00001 = $0.002       | Langfuse: ~1% của total cost              |

**Mẫu tính toán per-run cụ thể**:

```
Task: "Điều tra vì sao doanh thu tuần X giảm"

Baseline run:
├─ Model input:       16k token (context + conversation) × $3/1M = $0.048
├─ Model output:      2k token × $15/1M                          = $0.030
├─ Retrieval:         2 queries + reranking                       = $0.005
├─ Tool calls:        DB query (3×), API call (1×)                = $0.015
├─ Infrastructure:    8s compute + 2GB temp memory                = $0.003
├─ Observability:     150 trace events                            = $0.001
│
└─ Total per run:     $0.102 (~10 cents)

At 1000 runs/day: 1000 × $0.102 = $102/day = $3,060/month
```

**Bài toán**: tối ưu xuống $0.05/run nhưng giữ quality ≥ 90%. Lợi nhuận $1,530/tháng.

### 1.3 Latency Model

Tổng latency per-agent-run:

$$T_{\text{total}} = T_{\text{model}} + T_{\text{tool}} + T_{\text{retrieval}} + T_{\text{network}} + T_{\text{queue}} + T_{\text{serialization}}$$

Phân tích từng thành phần (P95 để ước lượng worst-case):

| Thành phần            | Công thức                                    | P95 Baseline | Optimized target | Chiến lược tối ưu                 |
| --------------------- | -------------------------------------------- | ------------ | ---------------- | --------------------------------- |
| **Model latency**     | Time for LLM inference (input → output)      | 3.2s         | 1.8s             | Smaller model, batch, cache       |
| **Tool latency**      | Max(time for all tool calls)                 | 2.1s         | 0.8s             | Parallel, reduce calls, cache     |
| **Retrieval latency** | time(query embedding + vector search + rank) | 0.6s         | 0.3s             | Filter early, cached index        |
| **Network latency**   | RTT: client ↔ server, server ↔ LLM provider  | 0.4s         | 0.2s             | CDN, closer region, HTTP/2        |
| **Queue latency**     | Time waiting for worker to pick up task      | 0.9s         | 0.2s             | More workers, dynamic scaling     |
| **Serialization**     | Encoding context, encoding tool args         | 0.3s         | 0.1s             | Binary format, schema pre-compile |
| │                     |
| └─ **Total P95**      | Sum                                          | **7.5s**     | **3.4s**         | 55% reduction                     |

**Critical path** = bottleneck lớn nhất. Ví dụ nếu model latency là 3.2s (42% tổng), tối ưu model trước.

### 1.4 Sáu vùng tối ưu

#### A. Model Optimization

| Kỹ thuật                | Trade-off                                       | Cost impact                      | Latency impact        |
| ----------------------- | ----------------------------------------------- | -------------------------------- | --------------------- |
| **Smaller model**       | Accuracy ↓ 2–5%, latency & cost ↓ 40–60%        | ↓ 60% (claude-haiku vs sonnet)   | ↓ 50%                 |
| **Model routing**       | Route simple Q to small model, complex to large | ↓ 35% (avg)                      | ↓ 25%                 |
| **Batch processing**    | 10 requests 1 batch thay vì 10 calls riêng      | ↓ 8% (fewer overhead), ↑ latency | ↑ 30%                 |
| **Lower temp (0 vs 1)** | Deterministic output, less token waste          | ↓ 5–10%                          | ↓ 3% (shorter output) |
| **Max tokens control**  | Cắp ngắn output trước khi model toàn quyền      | ↓ 20–50%                         | ↓ 20%                 |

**Quyết định**: "Đi down từ Sonnet 4 xuống Haiku sẽ làm giảm cost 60% nhưng accuracy từ 92% xuống 87%. Có chấp nhận không?"

#### B. Context Optimization

| Kỹ thuật                     | Cách làm                                     | Tiết kiệm token | Rủi ro                    |
| ---------------------------- | -------------------------------------------- | --------------- | ------------------------- |
| **Compression**              | Remove whitespace, collapse repeated tokens  | 5–10%           | Không đáng kể             |
| **Summarization**            | Tóm tắt message cũ thành bullet points       | 30–50%          | Mất chi tiết, hallucinate |
| **Retrieval filtering**      | Chỉ lấy top-5 instead top-20 relevant docs   | 20–40%          | Miss niche info           |
| **Remove redundant context** | Model prompt caching, skip unchanged history | 40–70%          | Logic bug nếu cache stale |
| **Sliding window**           | Keep only last N messages, flush older ones  | 60–80%          | Lose long-term context    |

**Công thức**: input_tokens_after = input_tokens_before × (1 − compression_ratio)

#### C. Tool Optimization

| Kỹ thuật                     | Áp dụng                                                     | Cost/latency  | Trade-off             |
| ---------------------------- | ----------------------------------------------------------- | ------------- | --------------------- |
| **Parallel tool calls**      | Chạy 3 DB queries cùng lúc thay vì tuần tự                  | ↓ latency 60% | Need connection pool  |
| **Tool result caching**      | Cache SQL query kết quả 5 phút                              | ↓ cost 40%    | Stale data risk       |
| **Reduce unnecessary calls** | Heuristic: nếu (X < threshold) skip verify step             | ↓ cost 15%    | Type 2 error possible |
| **Better tool granularity**  | Split `query_db` thành `query_users` + `query_transactions` | ↓ cost 10%    | More tool definitions |
| **Tool result truncation**   | Cắp ngắn tool result nếu > 2k char                          | ↓ cost 5%     | Info loss             |

#### D. Retrieval Optimization

| Kỹ thuật                    | Cách                                                            | Cost/latency impact |
| --------------------------- | --------------------------------------------------------------- | ------------------- |
| **Pre-filtering**           | Metadata filter trước query, giảm từ 10k → 1k documents         | ↓ latency 80%       |
| **Cached embeddings**       | Reuse embedding của query thường gặp                            | ↓ cost 50%          |
| **Reranking selective**     | Chỉ rerank top-10 thay vì top-100                               | ↓ cost 30%          |
| **Hybrid retrieval (BM25)** | BM25 fast path first, hybrid nếu cần                            | ↓ latency 40%       |
| **Vector quantization**     | 8-bit vectors thay vì 32-bit, giảm index size 4×, latency 20% ↓ | ↓ cost 25%          |

#### E. Infrastructure Optimization

| Kỹ thuật                  | Áp dụng                                           | Cost impact | Latency impact |
| ------------------------- | ------------------------------------------------- | ----------- | -------------- |
| **Connection pooling**    | Reuse DB connections thay vì tạo mới mỗi request  | ↓ 5%        | ↓ 15%          |
| **Concurrency tuning**    | Increase from 10 → 50 workers                     | —           | ↓ 40%          |
| **Autoscaling**           | Scale down during off-peak, save 60% infra cost   | ↓ 60%       | —              |
| **Caching layer (Redis)** | Cache agent responses 10 min (duplicate requests) | ↓ 45%       | ↓ 90%          |
| **CDN for assets**        | Serve cached context từ edge locations            | ↓ 10%       | ↓ 30%          |

#### F. Observability Trade-off

| Kỹ thuật               | Thay đổi                                       | Cost impact | Trade-off          |
| ---------------------- | ---------------------------------------------- | ----------- | ------------------ |
| **Sampling traces**    | Log 1/10 requests thay vì toàn bộ              | ↓ 90%       | Miss rare failures |
| **Async logging**      | Không block request, log background            | ↓ 5%        | Loss on crash      |
| **Compression traces** | Gzip events trước gửi                          | ↓ 40%       | CPU overhead       |
| **Cheaper provider**   | Migrate từ Langfuse → Open Telemetry self-host | ↓ 80%       | DevOps overhead    |

### 1.5 AI Gateway: Orchestrator của Optimization

Trong production, không tối ưu "manual". Cần **AI Gateway** — một lớp control plane:

```text
┌─────────────────────────────────┐
│         Client Request          │
└────────────────┬────────────────┘
                 │
        ┌────────▼────────┐
        │   AI Gateway    │
        │                 │
        │ • Rate Limiting │
        │ • Usage Tracking│
        │ • Model Routing │
        │ • Caching       │
        │ • Load Balance  │
        │ • Model Fallback│
        └────────┬────────┘
                 │
        ┌────────┴────────┬──────────────┬──────────┐
        │                 │              │          │
    ┌───▼──┐         ┌────▼─┐      ┌───▼──┐  ┌───▼──┐
    │Sonnet│         │Haiku │      │Opus  │  │Cache │
    │ 4    │         │      │      │      │  │      │
    └──────┘         └──────┘      └──────┘  └──────┘
```

**Tính năng AI Gateway**:

| Feature            | Mục đích                                                     | Trade-off                      |
| ------------------ | ------------------------------------------------------------ | ------------------------------ |
| **Routing**        | Route based on complexity (simple → Haiku, complex → Sonnet) | Need complexity classifier     |
| **Load balancing** | Spread requests across providers để không vượt quota         | Multi-provider management      |
| **Rate limiting**  | Per-user, per-model, per-API limit để kiểm soát cost         | User experience nếu limit low  |
| **Usage tracking** | Real-time cost per user/feature → chargeback, alerts         | Overhead logging               |
| **Model fallback** | Nếu Sonnet unavailable → use Opus (backup, expensive)        | More cost dự phòng             |
| **Caching**        | Cache responses, return cache hit nếu identical request      | Stale data, cache invalidation |

Các sản phẩm: Anthropic Batch API, vLLM, LiteLLM, Portkey, Kong API Gateway.

## 2. Deep dive — Phân tích Bottleneck & ROI (25 phút)

### 2.1 Framework: Bottleneck Analysis

**Bước 1: Collect Traces** (từ Langfuse)

Xuất tất cả runs từ baseline evaluation. Mục tiêu: 100+ runs để có P50, P95, P99.

```sql
-- Langfuse: query model, tokens, latency
SELECT
  run_id,
  model_name,
  input_tokens,
  output_tokens,
  latency_ms,
  cost_usd,
  eval_metric (e.g., task_success_0/1)
FROM runs
WHERE created_at > DATE_SUB(NOW(), INTERVAL 7 DAY)
ORDER BY latency_ms DESC
LIMIT 100;
```

**Bước 2: Classify by Percentile**

| Percentile | Latency | Impact      | Action                          |
| ---------- | ------- | ----------- | ------------------------------- |
| P50        | 2.1s    | Median user | Accept, but look for quick wins |
| P95        | 7.5s    | Worst 5%    | Must fix if SLA is 5s           |
| P99        | 12.3s   | Worst 1%    | Acceptable to have tail latency |

**Bước 3: Identify Bottleneck**

Vẽ biểu đồ **component latency breakdown** từ trace:

```
Total latency P95: 7.5s
├─ Model inference:    3.2s (42%) ← bottleneck #1
├─ Tool execution:     2.1s (28%) ← bottleneck #2
├─ Retrieval:          0.6s (8%)
├─ Network RTT:        0.4s (5%)
├─ Queue wait:         0.9s (12%)
└─ Serialization:      0.3s (4%)
```

**Critical path** = Model (3.2s) + Tool (2.1s) = 70% tổng latency.

**Bước 4: Hypothesis**

- Model latency cao vì context lớn (16k tokens) → solution: context compression.
- Tool latency cao vì tuần tự chạy 3 DB queries → solution: parallel calls.

### 2.2 Trade-off Matrix

Mỗi tối ưu có cost, latency, quality trade-off. Bảng quyết định:

| Optimization        | Cost reduction  | Latency reduction | Quality impact | Implementation effort | ROI                     |
| ------------------- | --------------- | ----------------- | -------------- | --------------------- | ----------------------- |
| Context compression | 25%             | 15%               | −2%            | 4h                    | High                    |
| Model routing       | 35%             | 20%               | −1%            | 8h                    | High                    |
| Parallel tools      | 0% (same tools) | 45%               | 0%             | 2h                    | High                    |
| Result caching      | 40%             | 60%               | +1% (fresh)    | 6h                    | Very high               |
| Smaller model       | 60%             | 50%               | −5%            | 1h                    | Medium (depends on SLA) |

**Quyết định chiến lược**:

1. Nếu SLA chặt (latency < 3s), tối ưu latency trước.
2. Nếu cost đang chảy máu (> $10k/month), tối ưu cost trước.
3. Nếu quality không thỏa (task success < 85%), tối ưu quality trước.

**Nguyên tắc**: giải quyết bottleneck lớn nhất trước, vì diminishing returns.

### 2.3 ROI Calculation

$$\text{ROI} = \frac{\text{Cost Saved} - \text{Implementation Cost}}{\text{Implementation Cost}} \times \frac{1}{1 + \text{Quality Regression}}$$

**Ví dụ cụ thể**:

```
Optimization: Context compression + caching

Baseline:
├─ Cost per run: $0.10
├─ Monthly volume: 1M runs
├─ Monthly cost: $100k
└─ Eval: task_success 90%

After optimization:
├─ Cost per run: $0.065 (35% reduction)
├─ Monthly volume: 1M runs
├─ Monthly cost: $65k
├─ Monthly saving: $35k
└─ Eval: task_success 88% (−2%)

Implementation:
├─ Engineering: 20 hours × $100/h = $2k
├─ Testing/validation: 10 hours = $1k
├─ Total: $3k

ROI = ($35k - $3k) / $3k × (1 / (1 + 0.02)) = $32k / $3k × 0.98 = 10.4 × 0.98 ≈ 10.2×

Payback period: $3k / ($35k / month) ≈ 0.09 month = 2.6 days
```

Nếu quality regression ≥ 5%, ROI rơi vào "medium" zone.

### 2.4 Quality Gate & Regression Test

Không được phép regression > defined threshold.

```python
# Langfuse: thiết lập quality gate
quality_gate = {
    "task_success": 0.90,     # minimum 90%
    "regression_threshold": 0.02  # allow max 2% drop
}

baseline_metric = 0.92
candidate_metric = 0.89
regression = (baseline_metric - candidate_metric) / baseline_metric
# regression = 0.0326 = 3.26% > 2% threshold → FAIL, roll back
```

**Bước 2: Compute Percentiles**

```python
import json
import numpy as np

traces = [json.loads(line) for line in open('baseline_traces.jsonl')]
latencies = [t['latency_ms'] for t in traces]

print(f"Latency P50: {np.percentile(latencies, 50):.1f}ms")
print(f"Latency P95: {np.percentile(latencies, 95):.1f}ms")
print(f"Latency P99: {np.percentile(latencies, 99):.1f}ms")
print(f"Mean: {np.mean(latencies):.1f}ms")

costs = [t['cost_usd'] for t in traces]
print(f"\nCost mean: ${np.mean(costs):.4f}")
print(f"Cost median: ${np.median(costs):.4f}")
print(f"Cost total (100 runs): ${np.sum(costs):.2f}")
```

**Output ví dụ**:

```
Latency P50: 2100ms
Latency P95: 7500ms
Latency P99: 12200ms
Mean: 3800ms

Cost mean: $0.1024
Cost median: $0.0987
Cost total (100 runs): $10.24
```

**Bước 3: Breakdown Components**

Langfuse cung cấp `span` data — mỗi span là một phần của flow.

```python
# Extract spans từ một trace
trace = traces[0]  # lấy trace slow nhất
print(f"Trace {trace['run_id']}: total {trace['latency_ms']}ms")

for span in trace.get('spans', []):
    print(f"  {span['name']}: {span['end_time'] - span['start_time']}ms ({span['metadata']})")

# Expected output:
# context_builder: 120ms
# model_inference: 3200ms ← BOTTLENECK

# result_formatting: 80ms
```

**Bước 4: Identify Bottleneck**

Từ breakdown, model inference (3200ms) + tool execution (2100ms) = 5.3s / 7.5s = 70%.

Giả thuyết: model chậm vì context = 16k tokens. Tool chậm vì 3 DB queries tuần tự.

**Optimization A: Context Compression**

```python
def compress_context(messages: list[dict]) -> list[dict]:
    """Summarize old messages, keep recent turns + summary"""
    if len(messages) <= 5:
        return messages  # keep recent

    old_messages = messages[:-5]
    recent = messages[-5:]

    # Summarize old messages into one
    summary_prompt = f"Summarize this conversation in 2 sentences:\n"
    for msg in old_messages:
        summary_prompt += f"{msg['role']}: {msg['content'][:200]}...\n"

    summary = client.messages.create(
        model="claude-haiku",
        max_tokens=150,
        messages=[{"role": "user", "content": summary_prompt}]
    ).content[0].text

    return [
        {"role": "user", "content": f"[Previous summary]: {summary}"},
        *recent
    ]

# Usage in agent
messages = compress_context(state["messages"])
model_response = client.messages.create(
    model="claude-sonnet-4",
    messages=messages,
    tools=TOOLS
)
```

**Optimization B: Parallel Tool Execution**

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def execute_tools_parallel(tool_calls: list[dict]) -> list[dict]:
    """Execute tool calls in parallel instead of sequentially"""
    results = []

    with ThreadPoolExecutor(max_workers=5) as executor:
        # Submit all tool calls
        futures = {
            executor.submit(run_tool, tc["name"], tc["input"]): tc["id"]
            for tc in tool_calls
        }

        # Collect results as they complete
        for future in as_completed(futures):
            tool_use_id = futures[future]
            try:
                result = future.result()
                results.append({
                    "type": "tool_result",
                    "tool_use_id": tool_use_id,
                    "content": json.dumps(result)
                })
            except Exception as e:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": tool_use_id,
                    "is_error": True,
                    "content": str(e)
                })

    return results

# Usage
tool_calls = extract_tool_calls(response)
if len(tool_calls) > 1:
    results = execute_tools_parallel(tool_calls)  # chạy song song
else:
    results = [execute_tool(tool_calls[0])]  # chạy tuần tự
```

**Optimization C: Model Routing (Advanced)**

```python
def classify_complexity(task: str, context_size: int) -> str:
    """Classify task complexity to route to appropriate model"""
    # Simple heuristic: if context small and task straightforward
    keywords_simple = ["list", "count", "summarize", "find"]
    keywords_complex = ["analyze", "compare", "investigate", "debug"]

    if any(k in task.lower() for k in keywords_simple) and context_size < 5000:
        return "haiku"  # fast, cheap
    elif any(k in task.lower() for k in keywords_complex):
        return "sonnet"  # powerful, expensive
    else:
        return "opus"  # fallback, most capable

def agent_with_routing(task: str, context: str) -> str:
    model = classify_complexity(task, len(context))
    print(f"[routing] complexity=?, model={model}")

    response = client.messages.create(
        model=f"claude-{model}-4",
        max_tokens=1024,
        messages=[
            {"role": "user", "content": f"{context}\n\n{task}"}
        ]
    )
    return response.content[0].text
```

- 2–3 học viên trình bày optimization report.

  - Bottleneck nào được chọn và tại sao.

### Câu hỏi kiểm tra cuối buổi

1. Chi phí per-run gồm những thành phần nào? Nếu muốn giảp 50%, thành phần nào cần tối ưu?
2. Latency critical path trong agent là gì (model vs tool vs retrieval)? Tối ưu cái nào trước?
3. Context compression giảm được bao nhiêu input token? Trade-off là gì?
4. Parallel tool execution giảm latency mấy %? Có rủi ro gì?
5. ROI calculation: nếu implementation cost $5k, monthly saving $2k, quality drop 3%, ROI là bao nhiêu? Có nên làm?
6. Khi nào KHÔNG nên tối ưu cost/latency (ví dụ, khi quality regression quá cao)?
